# Migrating from Taskferry 0.1 to 0.2

0.2 is a breaking release. The refactor changed what Taskferry *is* — from a family
of four Django-adjacent primitives to a portable execution layer — and several of
the 0.1 boundaries could not survive that intact.

This guide is mechanical: every 0.1 symbol, and what replaces it.

## Why it broke

Two changes forced the rest:

1. **`taskferry` became a regular package** so it could ship a public API.
   `from taskferry import Taskferry` was structurally impossible under the 0.1 PEP
   420 namespace layout ([ADR-0013](../adr/0013-packaging-strategy.md)).
2. **Tasks became framework-agnostic.** In 0.1 a task *was* a Django task
   ([ADR-0001](../adr/0001-portable-execution-layer.md)).

## Install

```diff
- pip install taskferry-django taskferry-jobs
+ pip install taskferry taskferry-django taskferry-procrastinate taskferry-cloudrun
```

`taskferry-core` no longer exists as a separate distribution; it is absorbed into
`taskferry`. Depend on `taskferry` instead.

## Import paths

| 0.1 | 0.2 |
| --- | --- |
| `taskferry.core` | `taskferry.core` *(unchanged, now shipped by `taskferry`)* |
| `taskferry.jobs` | `taskferry_jobs`, plus `taskferry` and `taskferry-cloudrun` |
| `taskferry.events` | `taskferry_events` |
| `taskferry.scheduler` | `taskferry_scheduler` |
| `taskferry.django` | `taskferry_django` |

A find-and-replace handles most of it:

```bash
grep -rl 'taskferry\.\(jobs\|events\|scheduler\|django\)' src/ | xargs sed -i '' \
  -e 's/taskferry\.jobs/taskferry_jobs/g' \
  -e 's/taskferry\.events/taskferry_events/g' \
  -e 's/taskferry\.scheduler/taskferry_scheduler/g' \
  -e 's/taskferry\.django/taskferry_django/g'
```

## Jobs

The `JobRunner` port became the `JobBackend` port, and jobs are now submitted
through the runtime rather than by indexing a global registry.

```diff
- from taskferry.jobs import JobSpec, runners
-
- handle = runners["default"].run(JobSpec(name="etl", command=["python", "etl.py"]))
- result = runners["default"].get(handle)
- if result.status == JobStatus.SUCCEEDED:
-     ...
+ from taskferry import Taskferry
+
+ runtime = Taskferry.local()          # or Taskferry.from_env()
+ handle = runtime.jobs.submit("etl", command=["python", "etl.py"])
+ if handle.wait(300).is_successful:
+     ...
```

### Type renames

| 0.1 | 0.2 |
| --- | --- |
| `JobRunner` | `JobBackend` (`taskferry.ports`) |
| `BaseJobRunner` | `BaseBackend` (`taskferry.ports`) |
| `JobHandle` | `ExecutionHandle` (`taskferry`) |
| `JobResult` | `ExecutionResult` (`taskferry`) |
| `JobStatus` | `ExecutionState` (`taskferry`) |
| `JobResources` | `Resources` (`taskferry`) |
| `JobCapability` | `Capability` (`taskferry`) |
| `runners` registry | `Taskferry` routing + configuration |
| `JobError` | `BackendError` / `SubmissionError` (`taskferry.errors`) |
| `JobNotFoundError` | `ExecutionNotFound` (`taskferry.errors`) |

### Status values

`JobStatus.PENDING` split into `ExecutionState.PENDING` (accepted by Taskferry, not
yet by the engine) and `ExecutionState.QUEUED` (accepted by the engine, waiting
for capacity). `TIMED_OUT` is new — 0.1 reported timeouts as `FAILED`.

### JobSpec fields

```diff
  JobSpec(
-     name="build-cog",
+     job="build-cog",
      image="gdal:latest",
      command=["python", "build.py"],
-     timeout=3600,
+     timeout=TimeoutPolicy(seconds=3600),
-     max_retries=2,
+     retry=RetryPolicy(max_attempts=3),
-     provider_options=ProviderOptions({"gcp": {...}}),
+     backend_options=BackendOptions({"cloudrun": {...}}),
  )
```

Note the retry change: `max_retries=2` meant two *re*-tries; `max_attempts=3`
means three attempts in total. See
[ADR-0011](../adr/0011-retry-ownership.md).

### Runner moves

| 0.1 | 0.2 |
| --- | --- |
| `taskferry.jobs.runners.local.LocalJobRunner` | `taskferry.backends.subprocess.SubprocessJobBackend` (built in) |
| `taskferry.jobs.runners.gcp.CloudRunJobsRunner` | `taskferry_cloudrun.CloudRunJobBackend` (own distribution) |
| `taskferry.jobs.runners.aws.BatchRunner` | `taskferry_jobs.BatchJobBackend` |
| `taskferry.jobs.runners.azure.ContainerAppsJobsRunner` | `taskferry_jobs.ContainerAppsJobBackend` |
| `taskferry.jobs.runners.kubernetes.KubernetesJobRunner` | `taskferry_jobs.KubernetesJobBackend` |

## Django

The Django-coupled provider backends are gone. Each was doing two jobs — talking
to a provider and satisfying Django's backend contract — and they are now
separated.

```diff
  TASKS = {
      "default": {
-         "BACKEND": "taskferry.django.backends.cloud_tasks.CloudTasksBackend",
-         "OPTIONS": {
-             "project": "my-project",
-             "location": "europe-west1",
-             "queue": "default",
-             "url": "https://svc.run.app/_taskferry/execute",
-         },
+         "BACKEND": "taskferry_django.TaskferryBackend",
      }
  }
+
+ TASKFERRY = {
+     "backends": {
+         "push": {
+             "factory": "cloudtasks",
+             "project": "my-project",
+             "location": "europe-west1",
+             "queue": "default",
+             "url": "https://svc.run.app/_taskferry/execute",
+         }
+     },
+     "defaults": {"task": "push"},
+ }
```

Your `@task` functions do not change.

| 0.1 | 0.2 |
| --- | --- |
| `taskferry.django.backends.local.LocalBackend` | `TaskferryBackend` + `{"factory": "thread"}` |
| `taskferry.django.backends.cloud_tasks.CloudTasksBackend` | `taskferry-cloudtasks` |
| `taskferry.django.backends.procrastinate.ProcrastinateBackend` | `taskferry-procrastinate` |
| `taskferry.django.backends.sqs.SQSBackend` | `taskferry-sqs` |
| `taskferry.django.backends.service_bus.ServiceBusBackend` | `taskferry-servicebus` |
| `taskferry.django.backends.dramatiq.DramatiqBackend` | `taskferry-dramatiq` |
| `taskferry.django.views.task_webhook` | `taskferry_django.views.task_webhook` (kept) or `taskferry_cloudtasks.handle_request` |
| `taskferry.django.consumers.process_sqs_event` | `taskferry_sqs.process_event` |
| `taskferry.django.consumers.process_sqs_message` | `taskferry_sqs.process_message` |
| `taskferry.django.TaskCapability` | `taskferry.Capability` |

### The receive side

`task_webhook` was a Django view. Its replacement takes bytes, so it works in any
framework:

```diff
- from taskferry.django.views import task_webhook
- urlpatterns = [path("_taskferry/execute", task_webhook)]
+ from django.http import HttpResponse
+ from taskferry import FunctionRegistry
+ from taskferry_cloudtasks import handle_request
+
+ REGISTRY = FunctionRegistry(allowed_modules=["myapp"])
+
+ def taskferry_execute(request):
+     handle_request(request.body, dict(request.headers), registry=REGISTRY)
+     return HttpResponse(status=204)
+
+ urlpatterns = [path("_taskferry/execute", taskferry_execute)]
```

Note the `allowed_modules` allowlist. 0.1's `resolve_task` imported any dotted
path from the message; this endpoint is reachable from the network, so 0.2 makes
restricting it the documented default posture. See [security.md](../security.md).

### The pull-based backends, now framework-agnostic

SQS, Azure Service Bus and Dramatiq were Django Tasks backends in 0.1. Each was
doing two jobs — talking to a provider and satisfying Django's backend contract —
so each is now its own distribution against the `TaskBackend` port, usable with or
without Django, and contract-tested.

```diff
- TASKS = {"default": {
-     "BACKEND": "taskferry.django.backends.sqs.SQSBackend",
-     "OPTIONS": {"queue_url": "https://sqs.eu-west-1.amazonaws.com/123/tasks"},
- }}
+ TASKS = {"default": {"BACKEND": "taskferry_django.TaskferryBackend"}}
+
+ TASKFERRY = {
+     "backends": {"sqs": {
+         "factory": "sqs",
+         "queue_url": "https://sqs.eu-west-1.amazonaws.com/123/tasks",
+     }},
+     "defaults": {"task": "sqs"},
+ }
```

```bash
pip install 'taskferry-sqs[aws]' 'taskferry-servicebus[azure]' 'taskferry-dramatiq[redis]'
```

The consumer side moved with them and no longer needs Django:

```diff
- from taskferry.django.consumers import process_sqs_event
+ from taskferry_sqs import process_event
```

`process_event` now also returns Lambda's `batchItemFailures`, so one poisonous
message no longer forces the whole batch to redeliver.

Dramatiq's actor is built explicitly rather than via `OPTIONS['actor']` alone:

```diff
- from taskferry.django.backends.dramatiq import build_execute_actor
- taskferry_execute = build_execute_actor()
+ from taskferry import FunctionRegistry
+ from taskferry_dramatiq import build_dispatch_actor
+ taskferry_execute = build_dispatch_actor(
+     registry=FunctionRegistry(allowed_modules=["myapp"]), max_retries=3
+ )
```

## Events and Scheduler

Only the module name changed. The contracts, adapters and registries are the same.

```diff
- from taskferry.events import Event, publishers
+ from taskferry_events import Event, publishers
```

## Configuration

0.1 configured each registry separately. 0.2 has one config object.

```diff
- from taskferry.jobs import runners
- runners.configure(settings.JOBS)
+ # settings.py
+ TASKFERRY = {
+     "backends": {...},
+     "routes": [...],
+     "defaults": {...},
+ }
```

Outside Django, `TaskferryConfig.from_env()`, `.from_mapping()` or `.local()`.

## Checklist

```bash
# 1. Update imports
grep -rn 'taskferry\.\(jobs\|events\|scheduler\|django\)' src/

# 2. Find registry indexing that should now be routing
grep -rn 'runners\[\|publishers\[\|schedulers\[' src/

# 3. Find status comparisons that need the new enum
grep -rn 'JobStatus\.' src/

# 4. Check the wiring end to end
python manage.py taskferry doctor      # Django
taskferry doctor                       # anywhere else
```

`doctor` builds every configured backend, so it catches a missing adapter, a
missing option and an unroutable kind in one pass.

## Deprecation policy

There are no shims. 0.1 was an early release, the boundaries it drew were the
thing being corrected, and a compatibility layer would have preserved exactly the
coupling this release removes — while making the migration ambiguous rather than
mechanical. Import errors are loud, immediate, and greppable; a silently working
deprecated path is none of those.
