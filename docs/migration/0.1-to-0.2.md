# Migrating from Taskport 0.1 to 0.2

0.2 is a breaking release. The refactor changed what Taskport *is* — from a family
of four Django-adjacent primitives to a portable execution layer — and several of
the 0.1 boundaries could not survive that intact.

This guide is mechanical: every 0.1 symbol, and what replaces it.

## Why it broke

Two changes forced the rest:

1. **`taskport` became a regular package** so it could ship a public API.
   `from taskport import Taskport` was structurally impossible under the 0.1 PEP
   420 namespace layout ([ADR-0020](../adr/0020-packaging-strategy.md)).
2. **Tasks became framework-agnostic.** In 0.1 a task *was* a Django task
   ([ADR-0011](../adr/0011-portable-execution-layer.md)).

## Install

```diff
- pip install taskport-django taskport-jobs
+ pip install taskport taskport-django taskport-procrastinate taskport-cloudrun
```

`taskport-core` no longer exists as a separate distribution; it is absorbed into
`taskport`. Depend on `taskport` instead.

## Import paths

| 0.1 | 0.2 |
| --- | --- |
| `taskport.core` | `taskport.core` *(unchanged, now shipped by `taskport`)* |
| `taskport.jobs` | `taskport_jobs`, plus `taskport` and `taskport-cloudrun` |
| `taskport.events` | `taskport_events` |
| `taskport.scheduler` | `taskport_scheduler` |
| `taskport.django` | `taskport_django` |

A find-and-replace handles most of it:

```bash
grep -rl 'taskport\.\(jobs\|events\|scheduler\|django\)' src/ | xargs sed -i '' \
  -e 's/taskport\.jobs/taskport_jobs/g' \
  -e 's/taskport\.events/taskport_events/g' \
  -e 's/taskport\.scheduler/taskport_scheduler/g' \
  -e 's/taskport\.django/taskport_django/g'
```

## Jobs

The `JobRunner` port became the `JobBackend` port, and jobs are now submitted
through the runtime rather than by indexing a global registry.

```diff
- from taskport.jobs import JobSpec, runners
-
- handle = runners["default"].run(JobSpec(name="etl", command=["python", "etl.py"]))
- result = runners["default"].get(handle)
- if result.status == JobStatus.SUCCEEDED:
-     ...
+ from taskport import Taskport
+
+ runtime = Taskport.local()          # or Taskport.from_env()
+ handle = runtime.jobs.submit("etl", command=["python", "etl.py"])
+ if handle.wait(300).is_successful:
+     ...
```

### Type renames

| 0.1 | 0.2 |
| --- | --- |
| `JobRunner` | `JobBackend` (`taskport.ports`) |
| `BaseJobRunner` | `BaseBackend` (`taskport.ports`) |
| `JobHandle` | `ExecutionHandle` (`taskport`) |
| `JobResult` | `ExecutionResult` (`taskport`) |
| `JobStatus` | `ExecutionState` (`taskport`) |
| `JobResources` | `Resources` (`taskport`) |
| `JobCapability` | `Capability` (`taskport`) |
| `runners` registry | `Taskport` routing + configuration |
| `JobError` | `BackendError` / `SubmissionError` (`taskport.errors`) |
| `JobNotFoundError` | `ExecutionNotFound` (`taskport.errors`) |

### Status values

`JobStatus.PENDING` split into `ExecutionState.PENDING` (accepted by Taskport, not
yet by the engine) and `ExecutionState.QUEUED` (accepted by the engine, waiting
for capacity). `TIMED_OUT` is new — 0.1 reported timeouts as `FAILED`.

### JobSpec fields

```diff
  JobSpec(
-     name="build-cog",
+     job="build-cog",
      image="gdal:latest",
      command=["python", "build.py"],
-     timeout=3600,
+     timeout=TimeoutPolicy(seconds=3600),
-     max_retries=2,
+     retry=RetryPolicy(max_attempts=3),
-     provider_options=ProviderOptions({"gcp": {...}}),
+     backend_options=BackendOptions({"cloudrun": {...}}),
  )
```

Note the retry change: `max_retries=2` meant two *re*-tries; `max_attempts=3`
means three attempts in total. See
[ADR-0019](../adr/0019-retry-ownership.md).

### Runner moves

| 0.1 | 0.2 |
| --- | --- |
| `taskport.jobs.runners.local.LocalJobRunner` | `taskport.backends.subprocess.SubprocessJobBackend` (built in) |
| `taskport.jobs.runners.gcp.CloudRunJobsRunner` | `taskport_cloudrun.CloudRunJobBackend` (own distribution) |
| `taskport.jobs.runners.aws.BatchRunner` | `taskport_jobs.BatchJobBackend` |
| `taskport.jobs.runners.azure.ContainerAppsJobsRunner` | `taskport_jobs.ContainerAppsJobBackend` |
| `taskport.jobs.runners.kubernetes.KubernetesJobRunner` | `taskport_jobs.KubernetesJobBackend` |

## Django

The Django-coupled provider backends are gone. Each was doing two jobs — talking
to a provider and satisfying Django's backend contract — and they are now
separated.

```diff
  TASKS = {
      "default": {
-         "BACKEND": "taskport.django.backends.cloud_tasks.CloudTasksBackend",
-         "OPTIONS": {
-             "project": "my-project",
-             "location": "europe-west1",
-             "queue": "default",
-             "url": "https://svc.run.app/_taskport/execute",
-         },
+         "BACKEND": "taskport_django.TaskportBackend",
      }
  }
+
+ TASKPORT = {
+     "backends": {
+         "push": {
+             "factory": "cloudtasks",
+             "project": "my-project",
+             "location": "europe-west1",
+             "queue": "default",
+             "url": "https://svc.run.app/_taskport/execute",
+         }
+     },
+     "defaults": {"task": "push"},
+ }
```

Your `@task` functions do not change.

| 0.1 | 0.2 |
| --- | --- |
| `taskport.django.backends.local.LocalBackend` | `TaskportBackend` + `{"factory": "thread"}` |
| `taskport.django.backends.cloud_tasks.CloudTasksBackend` | `taskport-cloudtasks` |
| `taskport.django.backends.procrastinate.ProcrastinateBackend` | `taskport-procrastinate` |
| `taskport.django.backends.sqs.SQSBackend` | `taskport-sqs` |
| `taskport.django.backends.service_bus.ServiceBusBackend` | `taskport-servicebus` |
| `taskport.django.backends.dramatiq.DramatiqBackend` | `taskport-dramatiq` |
| `taskport.django.views.task_webhook` | `taskport_django.views.task_webhook` (kept) or `taskport_cloudtasks.handle_request` |
| `taskport.django.consumers.process_sqs_event` | `taskport_sqs.process_event` |
| `taskport.django.consumers.process_sqs_message` | `taskport_sqs.process_message` |
| `taskport.django.TaskCapability` | `taskport.Capability` |

### The receive side

`task_webhook` was a Django view. Its replacement takes bytes, so it works in any
framework:

```diff
- from taskport.django.views import task_webhook
- urlpatterns = [path("_taskport/execute", task_webhook)]
+ from django.http import HttpResponse
+ from taskport import FunctionRegistry
+ from taskport_cloudtasks import handle_request
+
+ REGISTRY = FunctionRegistry(allowed_modules=["myapp"])
+
+ def taskport_execute(request):
+     handle_request(request.body, dict(request.headers), registry=REGISTRY)
+     return HttpResponse(status=204)
+
+ urlpatterns = [path("_taskport/execute", taskport_execute)]
```

Note the `allowed_modules` allowlist. 0.1's `resolve_task` imported any dotted
path from the message; this endpoint is reachable from the network, so 0.2 makes
restricting it the documented default posture. See [security.md](../security.md).

### The pull-based backends, now framework-agnostic

SQS, Azure Service Bus and Dramatiq were Django Tasks backends in 0.1. Each was
doing two jobs — talking to a provider and satisfying Django's backend contract —
so each is now its own distribution against the `TaskBackend` port, usable with or
without Django, and contract-tested.

```diff
- TASKS = {"default": {
-     "BACKEND": "taskport.django.backends.sqs.SQSBackend",
-     "OPTIONS": {"queue_url": "https://sqs.eu-west-1.amazonaws.com/123/tasks"},
- }}
+ TASKS = {"default": {"BACKEND": "taskport_django.TaskportBackend"}}
+
+ TASKPORT = {
+     "backends": {"sqs": {
+         "factory": "sqs",
+         "queue_url": "https://sqs.eu-west-1.amazonaws.com/123/tasks",
+     }},
+     "defaults": {"task": "sqs"},
+ }
```

```bash
pip install 'taskport-sqs[aws]' 'taskport-servicebus[azure]' 'taskport-dramatiq[redis]'
```

The consumer side moved with them and no longer needs Django:

```diff
- from taskport.django.consumers import process_sqs_event
+ from taskport_sqs import process_event
```

`process_event` now also returns Lambda's `batchItemFailures`, so one poisonous
message no longer forces the whole batch to redeliver.

Dramatiq's actor is built explicitly rather than via `OPTIONS['actor']` alone:

```diff
- from taskport.django.backends.dramatiq import build_execute_actor
- taskport_execute = build_execute_actor()
+ from taskport import FunctionRegistry
+ from taskport_dramatiq import build_dispatch_actor
+ taskport_execute = build_dispatch_actor(
+     registry=FunctionRegistry(allowed_modules=["myapp"]), max_retries=3
+ )
```

## Events and Scheduler

Only the module name changed. The contracts, adapters and registries are the same.

```diff
- from taskport.events import Event, publishers
+ from taskport_events import Event, publishers
```

## Configuration

0.1 configured each registry separately. 0.2 has one config object.

```diff
- from taskport.jobs import runners
- runners.configure(settings.JOBS)
+ # settings.py
+ TASKPORT = {
+     "backends": {...},
+     "routes": [...],
+     "defaults": {...},
+ }
```

Outside Django, `TaskportConfig.from_env()`, `.from_mapping()` or `.local()`.

## Checklist

```bash
# 1. Update imports
grep -rn 'taskport\.\(jobs\|events\|scheduler\|django\)' src/

# 2. Find registry indexing that should now be routing
grep -rn 'runners\[\|publishers\[\|schedulers\[' src/

# 3. Find status comparisons that need the new enum
grep -rn 'JobStatus\.' src/

# 4. Check the wiring end to end
python manage.py taskport doctor      # Django
taskport doctor                       # anywhere else
```

`doctor` builds every configured backend, so it catches a missing adapter, a
missing option and an unroutable kind in one pass.

## Deprecation policy

There are no shims. 0.1 was an early release, the boundaries it drew were the
thing being corrected, and a compatibility layer would have preserved exactly the
coupling this release removes — while making the migration ambiguous rather than
mechanical. Import errors are loud, immediate, and greppable; a silently working
deprecated path is none of those.
